# ARABA 사업자 회원·사업자 AI·통합 권한형 앱 설계안 v0.1 (승인 전 초안)

작성 기준: 2026-10-11
상태: REVIEW_REQUIRED (설계·검토 전용, 구현 및 main 병합 금지)

## 0. 확정 원칙
1. 지금 휴대폰에서 테스트하는 ARABA 앱은 관리자/개발 테스트용이다. 당장 이를 일반 사용자나 회원사용으로 바꾸지 않는다.
2. 상용화 단계에서는 **하나의 앱**에 사용자·회원사·플랫폼 관리자 역할을 함께 제공한다. 로그인한 사용자의 서버 측 권한에 따라 메뉴, 데이터 범위, 기능이 달라진다. 한 사람이 여러 역할이면 승인된 역할 전환을 제공한다.
3. 구현 전에 화면 흐름·DB 구조·AI 권한·대리업무 완료 기준을 사용자에게 설계로 제시하고 승인받는다.
4. 업체별로 질문/답변을 하드코딩하지 않는다. ARABA 공통 Agent 엔진 + 업체별 지식/정책 + 구조화된 권한 + 업종별 기능 어댑터로 구성한다.
5. ARABA Business Graph(DB)를 Source of Truth로 사용한다. AI 출력은 미확인 사실을 만들지 않고, 거래/예약/결제 확정에는 실제 실행 API와 권한 검증이 필요하다.
6. 한 메시지의 다중요청과 후속질문, 멀티턴 조율을 각각 유지한다. 과거 대화 전체만 던지는 방식보다 목표·조건·제안·미해결 항목·증거·현재 상태를 구조화 저장한다.

## 1. 현재 GitHub 기반 현황 / 새로 필요한 것
- 기존: backend/api/models.py의 Business, BusinessFact, BusinessExperience, BusinessRealtimeSignal; business_graph_service; business_matching_service; profile_schema_service의 사업자 가입/운영/권한/협상 스키마; business_agent_service의 외부 Agent HTTPS capability_check 프로토콜.
- 현 상태에는 사업자 소유권 Claim/사업자 인증/사업자 로그인 전용 API/점주 대시보드/권한 승인형 거래 워크플로의 실구현이 확인되지 않는다. 기존 스키마 정의와 실제 가입·회원사 AI 실행 기능을 혼동하지 않는다.
- Business를 중복 생성하지 않고 회원사 Account/Claim/관리권한/업체 지식/Agent 설정을 기존 Business에 FK로 연결한다.
- 현 개발 설정의 SQLite는 상용 다중사업자 사용 전 운영 DB, 동시성·백업·감사추적·마이그레이션을 별도 검토한다.

## 2. 역할·접근제어
- Consumer: 개인 검색·비교·대리업무, 본인 요청/결과만 접근.
- Merchant Owner: 본인이 인증해 소유한 1개 이상 사업장 관리, AI 정책 설정, 승인/거절, 정산.
- Merchant Staff/Manager: 초대 기반 사업장별 제한 권한(예약만, 상담만, 정산 조회 제외 등).
- Platform Admin: 전체 사업장 검증·고객지원·정책·비용·보안, 별도 권한 보호.
- 동일 계정에 복수 역할 가능: [개인 모드] / [회원사 A] / [회원사 B] / [관리자 모드]. 한 앱, 단일 인증, 역할별 내비게이션. 화면 숨김에 의존하지 않고 모든 API에 객체 단위 권한 확인.

## 3. 사업자 가입 / 기존 DB 연결 UX
단계 A 계정 생성: 아이디 중복 확인, 강한 비밀번호·확인 입력, 이메일/휴대전화 OTP 인증(선택한 수단), 약관·개인정보 동의, 로그인 보호(속도제한, 재시도 지연, 중요 변경 시 추가 인증).
단계 B 업체 검색: 상호명/주소/전화 등으로 기존 Business DB 검색; 유사명 업체를 주소·지도와 함께 비교. 본인 업체 선택 → '운영자 권한 신청(Claim)' 기록. 중복 Claim/이미 인증된 소유자 발견 시 자동 장악 금지, 심사·분쟁처리.
단계 C DB에 없다면 '새 사업장 임시 생성': 사업장명·업종·주소·대표 연락처·사업자등록번호·대표자명·사업자등록증 업로드. 임시 상태로 공공 노출이나 거래 확정은 제한.
단계 D 사업자 검증: 번호 유효성 확인과 실제 **해당 사업장의 운영권자임을 증명하는 것**은 다르다. 공식 검증 지원 시 비교하고, 소유자/위임 직원 증명은 서류 검토 또는 승인된 인증절차. 민감한 등록증 파일은 암호화·접근통제·보관기한·파기정책 적용, 공개 카드에는 노출 금지.
단계 E 기존 DB 미리 채움: 이름/주소/전화/업종/위치·확인 가능한 기존 Facts를 미리 표시하며 사업자가 확인·수정. 수정 내용은 출처/수정자/최종확인시각/검증등급 기록.
단계 F 회원사 운영 정보: 기본 필드(영업시간·휴무·전화·주차·주요 상품·가격·예약정책) + '우리 업체에 대해 자유롭게 설명해 주세요' 큰 텍스트 창 + 사진·파일·홈페이지 연동(선택).
단계 G AI 운영지침: 'AI는 고객과 어떻게 응대하고 무엇까지 결정할 수 있나요?' 자유 입력 + 권한 체크/숫자 상한에 대한 요약 검토 및 명시 승인.
단계 H 등록 완료: 계정=가입됨, 사업장 소유권=심사중/인증완료, AI=초안/시뮬레이션/승인 후 활성화. 각각 별도 상태.

## 4. 자유 텍스트 → 구조화 Business Schema
사업자가 '주차 8대, 단체 10명까지 가능, 토요일 10% 할인, 당일 취소 환불 불가' 등 자연어를 입력하면:
1. AI가 구조화 제안(JSON): 사실(fact), 운영규칙(policy), 상품/서비스(service), 예약/재고(availability), 협상 가능한 조건(negotiation), 금지/승인 필요(actions), 출처·확인시각(evidence).
2. 서로 모순되는 정보와 빈 필드 탐지. 질문은 꼭 필요한 것만 동적으로 묻는다(업종별 고정 설문 대량 구현 X).
3. 사업자 화면에서 '원문 ↔ AI 추출값'을 함께 보여주고 수정을 받는다.
4. 중요 권한은 자유 텍스트를 그대로 실행 권한으로 간주하지 않는다. 별도 Boolean/숫자/승인규칙을 운영자가 확인한 후 서버 정책으로 저장한다.
5. 변경 이력 및 유효기간: 실시간 재고·예약 가능 여부는 외부 예약/POS/캘린더 동기화나 직원 확인이 없으면 '확인 필요'.

## 5. 사업자 AI 공통 구조 (업체별 모델 훈련 X)
- 동일 공통 AI 런타임에서 business_id별 테넌트 영역으로 업체 지식·가격·서비스·운영정책·AI 말투·권한·이용 가능한 툴을 로딩해 세션 실행.
- 사용자의 AI는 '목표·예산·인원·시간·필수조건·개인정보 제공동의·결정허용범위'를 구조화한다.
- 사업자 AI는 '업체 사실·실시간 데이터·승인된 협상규칙·실행 가능 권한'을 활용해 응답한다.
- 별도 모델 학습(Fine-tuning)은 필수 아님. 문서 검색/RAG 및 Function Calling/도구 연결 사용. 사업자 데이터가 바뀌면 다음 호출에 반영.
- 권한 밖 요청은 거절/직원 승인/대안 제안 중 하나로 전환한다. 외부 웹/고객 발화는 지침보다 낮은 신뢰로 취급.
- 웹/API/직원 확인 근거가 없는 예약·가격·가능 여부는 확정 표현 금지.

## 6. 업종 불문 공통 협상·실행 엔진
'가능한 질문'을 미리 전수 코딩하는 대신 범용 행동 계약(Action Contract)을 정의한다:
  query_fact / ask_clarification / quote_price / check_availability / propose_terms / counter_offer / request_approval / place_temporary_hold / confirm_booking_or_order / modify / cancel / notify / handoff_to_human.
- 업종별로 기능 어댑터(adapter)만 추가한다: 예약/캘린더, POS/재고, 결제, 배송, 견적/전자서명 등. 연동이 없다면 제안·직원 확인까지만 진행.
- LLM은 제안하는 계획자, Policy Engine은 허용/거절하는 결정권자, 실행용 Tool Gateway는 실제 상태를 바꾸는 기록된 행위자. LLM이 DB 상태를 직접 '확정'해서는 안 된다.
- 두 AI의 내부 협의는 목표·조건·제안·반대제안·증거를 구조화하며 최대 왕복/시간/토큰·비용 제한을 둔다.
- 완료 조건은 거래별 계약으로 정의: 예약은 슬롯 실제 점유+확정번호, 주문은 주문ID+결제/재고 조건, 견적은 유효기간 포함 견적ID, 단순 정보조회는 근거 있는 답변. 공통 완료 상태지만 확인 증거는 유형별.
- 거래 상태: NEW → DISCOVERING → NEGOTIATING → AWAITING_USER_OR_MERCHANT_APPROVAL → HOLDING → CONFIRMED → COMPLETED (또는 FAILED/CANCELLED/EXPIRED/DISPUTED).
- 중복결제/중복예약 방지 키, 롤백/보상, 타임아웃/재시도, 사람 전환, 사용자 승인, 감사로그와 비용로그 필수.

## 7. AI 권한 4단계
L0 정보 응답: 사업자가 제공/확인한 사실만 안내. 초깃값.
L1 비구속 제안: 가격·조건·시간에 대한 제안을 만들되 확정 불가.
L2 제한된 자동확정: 서비스/금액/할인율/시간/인원·정책 내에서, 실시간 슬롯/재고/결제 조건 확인 후 확정.
L3 높은 위험·예외: 큰 할인, 환불, 계약, 분쟁, 규제업종의 민감업무는 사람 승인·추가 인증 후 진행.
- 모든 권한은 필드로 저장하고, 기본은 최소 권한(L0). 예: 할인 상한 10%, 총액 30만원, 오늘 남은 슬롯만, 당일 취소 환불은 사람 승인.
- 'AI 지침 자유 글'은 응대 톤·선호·금지규칙 후보로 쓰되, 해당 글이 L2/L3 권한을 부여할 수는 없다.
- 의료·법률·금융 등 업종은 별도 규제 점검 후 허용 행동 범위 결정.

## 8. 회원사 대시보드 구성 (모바일 우선, PC 반응형)
상단: 사업장 전환, AI ON/OFF, 인증상태, 오늘 거래/대기/승인필요/응답성공률.
주요 블록:
A. 'AI가 지금 처리 중' 라이브 요청함: 고객 요청 요약, 누락정보, 진행단계, 예정시간, 응답기한.
B. '내 승인 필요' 인박스: 할인 한도 초과/슬롯 모호/가격 확정/환불/예외의 승인·거절·수정 제안.
C. '거래·예약' 일정표 및 계약/견적/주문, 확정 증거/취소 이력.
D. '내 업체 정보' 기본정보·사진·서비스·가격·영업시간·정책·자료 업로드·출처/신선도.
E. 'AI 직원 설정' 자유 운영지침, 구조화된 권한, 연결된 업무 툴, 테스트 샌드박스, 버전기록.
F. '고객·통계' 상담문의, 포기이유, 충족/불일치 조건, AI 응답 품질, 성사율.
G. '이용료·정산' 요금제, AI 사용량/제한/월 사용료, 거래수수료, 영수증.
H. '직원·보안' 팀 권한, 로그인/변경내역, 다중 사업장.
- 모바일 하단 기본 메뉴: 홈 / 요청·승인 / 예약·거래 / AI 직원 / MY. 나머지는 관리 메뉴 내 묶기.
- 관리자 모드는 현재 테스트 기능을 유지하되 상용 일반 화면과 명확히 권한 분리.

## 9. 통합 앱 화면 라우팅
로그인 전: 검색/안내/가입.
개인 모드: 검색·대리업무·알림·내역·MY.
회원사 모드: 운영 현황·요청함·예약/거래·AI 직원·사업장 관리.
관리자 모드: 검증·모니터링·분쟁/승인·API원가/정산·감사로그·설정.
동일 계정 겸업 시 상단 역할/사업장 선택. API별 tenant_id+role 기반 접근 제어 필수.

## 10. DB 확장안
Business(기존 유지) 1:N BusinessClaim, BusinessMembership, BusinessEvidence, BusinessDocument, BusinessService, BusinessPolicy, AgentConfigurationVersion, BusinessIntegration, AgentSession, NegotiationThread, AgentMessage, ActionProposal, ApprovalRequest, Transaction/Booking, ExecutionEvent, UsageLedger.
- 인증계정 Django User 또는 확장모델 연결; 사업자등록번호는 암호화·마스킹·중복검증, 파일 별도 보호 스토리지.
- 원천 사실과 AI 추정/사용자 후기 데이터는 저장 계층 분리; 스냅샷 + 변경 이력과 출처.
- 모든 거래·협상·승인 내역은 business_id와 주체별 ACL·감사추적 적용.

## 11. MVP 및 단계적 적용
1단계: 역할·인증/가입·기존 DB Claim·권한 인증·사업장 기본 관리·자유입력 구조화·임시 AI 응대 (거래확정 없음).
2단계: 업체 AI 대화/판단 시뮬레이션·요청/승인함·관리자 검증·사용량 비용 모니터링.
3단계: 업종별 1~2개 실제 실행 어댑터를 통한 예약/확정/취소/알림, A2A 멀티턴 협상·계약 상태머신.
4단계: 결제/발주/B2B 확장, 권한·감사·운영 품질 강화.
- 테스트 승인 게이트: 중복 사업장 Claim, 무권한 접근, 잘못된 가격/슬롯 확정, prompt injection, 취소/중복요청, 두 개 이상의 요구 처리, 다중사업장 역할 전환, 장시간 협상/비용 한도.
- 개발 착수 전 사용자 검토 항목: 사업자 가입 필수값, 무료/유료 공개 범위, AI 자동확정의 기본 단계, 첫 실거래 업종 및 승인 흐름.

## 12. 승인 전 금지
- 이 문서는 초안일 뿐이며 현재 앱·API·DB 스키마·배포 서버에는 어떤 변경도 수행하지 않는다.
- 사용자의 명시적 승인 후 기존 실코드와 테스트를 확인해 중복 없이 단계별 구현한다.
