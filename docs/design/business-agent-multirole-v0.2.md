# ARABA 통합 앱·회원사 가입 및 기존 업체 DB 연결 설계 v0.2

상태: **사용자 승인에 따라 1차 구현 진행 중 / 배포 전 검증 필요**
반영 요청: 2026-10-14

## 승인한 방향
- 상용 ARABA 앱은 하나. 로그인 사용자의 서버 인증·사업장별 승인 권한으로 일반 사용자, 회원사, 관리자 UI를 다르게 제공한다.
- 현재 개발용 관리자 앱은 모든 흐름을 직접 테스트해야 하므로 **관리자 / 일반 사용자 / 사업자** 모드 전환 UI를 갖춘다. 전환은 UI 미리보기일 뿐 서버 권한을 부여하지 않는다.
- 회원사는 신규 업체를 중복 만들기 전 기존 ARABA Business Graph 내 상호명/주소로 검색한다. 검색 결과에서 본인 사업장을 선택하고 사업장 관리권한을 신청한다.
- 소유권 인증 전에는 수정 초안만 저장한다. 인증 이후 사업주가 업체 기본정보·추가정보를 수정하면 기존 Business 레코드에 반영한다. 인증 소유권과 본인 사업장 여부는 서버에서 검사한다.
- 추가정보와 사업자 AI 운영지침은 자유로운 긴 텍스트 입력을 지원하지만 AI 운영지침은 실제 할인·예약·결제 자동 실행권한이 아니다. 향후 별도 구조화 정책 확인 및 실행 Tool Gateway 도입이 필요하다.
- 관리자 테스트 앱은 API 키/상점DB/교육/훈련 등 기존 기능을 유지한다. 일반 사용자 화면에서는 관리자 API 키 정보를 보여주지 않는다.

## 기존 자산 재사용
- `Business`: 검색된 업체의 실체, 신규 중복 생성 금지.
- `BusinessFact`: 인증된 사업자 정보의 출처와 값 관리.
- `BusinessClaim`: 로그인 계정 ↔ 기존 Business 연결, 소유권 심사, 등록번호 비원문 저장, 본인 정보 변경 초안.
- `business_graph_service`: 사업주 확인 정보 우선권, 외부 검색 데이터 재수집 시 덮어쓰기 방지.
- `profile_schema_service`: 이미 제안된 사업자 스키마/AI권한/협상 데이터 구조.
- `business_agent_service`: 기존 외부 에이전트 capability check. 사업장별 AI 직원 실제 협상·예약 완료 엔진은 후속 단계.

## 1차 테스트 흐름
1. 관리자 테스트 앱 실행 → 상단 '관리자 / 사용자 / 사업자' 탭 전환
2. 관리자: 기존 앱의 검색, 상점DB, API 진단 등 모든 테스트 화면 유지
3. 사용자: 일반 검색 화면과 MY 화면 표시 (관리자 전용 키 설정 감춤)
4. 사업자: 아이디 중복검사 + 비밀번호 재입력 + 약관 동의 후 가입/로그인
5. 본인 상호명 검색 → 기존 DB 업체와 주소 확인 → 본인 사업장 선택
6. 대표자명, 사업자등록번호, 연락처 입력 → BusinessClaim 심사 대기
7. 기존 업체 필드 자동채움 → 정보 수정/긴 텍스트 추가정보/AI 지침 초안 저장
8. Django 관리자에서 외부 서류·실제 운영권 확인 후 관리자 승인 (별도 승인 절차)
9. 인증된 사업주는 다시 로그인/동기화 후 실제 업체 정보 수정·저장 가능
10. 다른 사업장 Claim의 정보 변경, 인증 없는 공개 DB 수정, 타 업체 무단 점유는 거절

## 중요한 보안·운영 미완료 단계
- 등록증 파일은 적절한 비공개 GCS 등 보안 객체저장소, 권한, 악성파일 검증, 보존·파기 규칙 마련 후 붙인다. 1차 MVP에서 파일을 무보호 서버에 저장하지 않는다.
- 가입 시 이메일/휴대전화 OTP, 비밀번호 복구, 2FA, 계정잠금, 실서비스 약관/개인정보 처리방침, 관리자 계정 인증/감사로그, 비정상 가입 제한은 상용화 전 완료해야 한다.
- 관리자 역할 전환은 **debug 전용 UI 미리보기**다. 출시 시 서버에서 가져온 UserRole/Membership에 따라 실제 화면과 API 권한을 제어한다.
- 실서비스 운영DB는 SQLite를 그대로 쓰지 말고 Cloud SQL/PostgreSQL 등 백업·복원·마이그레이션/접근통제 기반으로 이전 계획을 승인받는다.
- `rest_framework.authtoken`과 `BusinessClaim` 마이그레이션을 서버에 적용하지 않으면 모바일 화면만 업데이트해도 가입·소유권 API는 사용불가.
- 기존 `/api/admin/businesses/`의 공개 접근 가능성 등 이전 시험용 엔드포인트 권한도 상용화 전 전수감사 필요.

## 후속 개발 (사용자 검토 유지)
1. 실제 사용자 로그인과 역할별 서버 API 전체 ACL, 신원 검증/등록증 제출
2. 사업자 AI 자연어 → 사실·정책·협상조건 구조화 승인 + 버전 관리
3. 사업자 대시보드: 오늘 요청, AI 협의, 승인대기, 예약·거래, 통계·비용
4. 업무별 도구 어댑터와 초안→양측승인→실제 실행·확정번호의 A2A 엔진
5. 다중사업장·직원 역할, 알림/사용량/정산, 감사 로그·비용 제어

## 이번 단계에서 하지 않는 것
- 인증 안 된 사업자의 공개 업체정보 즉시 변경
- 회원사마다 별도 모델 훈련하거나 질문마다 조건문 하드코딩
- AI가 자유 지침만 보고 실제 할인을 확정하거나 예약·결제를 실행
- 상용 사용자 계정에 관리자 개발용 API 키/디버깅 UI 노출
